Orchestra

One overseer that talks a task through, writes the brief, then builds, tests and reviews it into a pull request with little hand-holding. Codex does the implementation; Claude and Codex share the reviewing.

overseer:claudeoverseer:codex/discussion/create-brief/do

Which command do I use?

You haveUseWhat happens
A question about the code, the ecosystem, or a failure/discussionEach question goes to the right specialist, and decisions land in tmp/discussions/.
A feature or bug that isn't written up/create-briefA brief.html with mockups, which you confirm and Socrates challenges.
A ready brief, Linear item or URL/doThe full run: plan, implement, verify, PR, review and QA, wrap-up.
Something broken you want diagnosed/investigateOne investigator finds the cause without fixing it.
Changes you already made in the session/prepare-pull-requestTurns them into a clean pull request.
A goal like “this metric reaches that target”/do with hillclimbRuns the implement step as a measured improvement loop.

The Claude overseer launches Codex roles with codex exec: the implementer (Sol medium, kept for fix rounds) and short-lived Sol low runs for backend verification, plan review, code review, code research and investigation. If Codex is unavailable, each role falls back to its Claude counterpart.

What /do does

  1. Preflight and load. Lists any missing credentials in one message, loads the item into tmp/<id>/, and stops if you're on the default branch.
  2. Plan. The zone sets the review lanes, loop caps and how much research to do. It writes a research dossier and plan.md, and can try competing candidates with arena.
  3. Implement. The Codex implementer builds it test-first.
  4. Verify. The backend verifier checks it against rubrics. UI checks wait for step 5.
  5. Pull request. Build gate, deploy-notes scan, a selective commit, and a structured PR body.
  6. Review, then QA. Review repeats until a pass has no Must Fix findings, then the frontend and backend verifiers drive QA. Evidence goes to a qa-assets prerelease, never into the repo.
  7. Wrap-up. Writes wrapup.md, labels the PR awaiting-human-review, updates Linear, and runs a postmortem.

Safety and attention

  • Green actions, like code and reversible staging changes, run unattended.
  • Red actions, like anything touching production or anything irreversible, need your approval in the session. Otherwise they are recorded and you are notified.
  • Notifications go out through ntfy.sh. Nothing received there can approve an action.
  • babysit-pr watches CI and bot reviews and merges only if you asked it to.

Where things go

Working files live in tmp/<id>/, or wherever the repository's AGENTS.md says. A companion Grain folder under Development Artifacts/ is renamed to PR-<n>-<title> once the PR exists. The PR body is the live dashboard, and PR comments carry the evidence.
